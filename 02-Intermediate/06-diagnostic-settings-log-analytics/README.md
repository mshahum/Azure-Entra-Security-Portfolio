# Centralizing Azure Activity Logs with Diagnostic Settings and Log Analytics

## Overview

This project focused on centralizing Azure Activity Logs into a Log Analytics workspace by using diagnostic settings at the subscription level.

Rather than only viewing activity events inside the Azure portal, this lab configured Azure to send management-plane activity logs into a searchable Log Analytics workspace. The objective was to create a stronger foundation for investigation, auditing, and security monitoring.

The lab was built around a practical cloud security scenario: administrative actions such as resource group creation, updates, deletions, role assignments, and policy changes should be retained and searchable so security teams can investigate who performed an action, when it happened, from which IP address, and whether it succeeded.

## Business Problem

Azure environments generate important management plane events whenever users create, update, delete, or configure resources. If these events are only viewed temporarily through the Activity Log interface, investigation and long term auditing become limited.

This creates a visibility problem. Security teams may need to investigate administrative actions after an incident, prove compliance during an audit, review suspicious configuration changes, or understand who changed a resource.

This project addressed that problem by sending Azure Activity Logs to a Log Analytics workspace, where events can be queried using KQL and used later for monitoring, investigation, and detection engineering.

## Project Objectives

This lab was designed to:

- create a dedicated resource group for centralized logging
- create a Log Analytics workspace
- configure subscription level diagnostic settings
- send Azure Activity Log categories to Log Analytics
- generate a real management plane test event
- validate log ingestion using KQL
- confirm that administrative events appeared in the `AzureActivity` table
- extract useful investigation fields such as operation name, status, caller, caller IP address, resource group, and category

## What Was Implemented

### 1. Logging Resource Group

A dedicated resource group named `RG-Logging-Lab` was created to organize the logging resources used in this lab.

Using a separate resource group helped keep the logging setup clean and easy to identify. This reflects a common enterprise pattern where monitoring and logging resources are separated from normal application workloads.

### 2. Log Analytics Workspace

A Log Analytics workspace named `LAW-Security-Logs-Lab` was created.

The workspace acted as the central location where Azure Activity Logs could be stored and queried. Once activity logs are sent into Log Analytics, they become much more useful for investigation and reporting because they can be searched with KQL.

### 3. Subscription Activity Log Export

The Azure Activity Log diagnostic settings page was used to configure log export from the subscription.

This is important because subscription-level Activity Logs capture management plane operations across Azure, such as resource creation, resource deletion, role assignments, policy changes, and other administrative actions.

### 4. Diagnostic Setting Configuration

A diagnostic setting named `DS-ActivityLogs-To-LAW` was created.

The diagnostic setting was configured to send Activity Log categories to the Log Analytics workspace. These categories included important management plane and platform events such as Administrative, Security, ServiceHealth, Alert, Recommendation, Policy, Autoscale, and ResourceHealth.

This enabled centralized collection of Azure platform logs for investigation and audit readiness.

### 5. Management Plane Test Event

A real management-plane event was generated by updating a resource group tag.

This test activity created a resource group write event in Azure Activity Logs. Generating a real event was important because the lab needed to validate actual log ingestion rather than only showing that diagnostic settings were configured.

### 6. KQL Validation

Kusto Query Language was used inside the Log Analytics workspace to query the `AzureActivity` table.

The query returned a successful resource group write event and displayed important investigation fields including operation name, activity status, activity substatus, resource group, caller, caller IP address, and category.

This confirmed that Azure Activity Logs were successfully reaching the Log Analytics workspace.

## Validation and Testing

The implementation was validated by generating a real Azure management plane event and then querying it in Log Analytics.

A resource group update action was performed by modifying tags. This created a resource group write event in the Activity Log.

The following KQL query was used to validate ingestion:

```kql
AzureActivity
| where TimeGenerated > ago(24h)
| where OperationNameValue =~ "MICROSOFT.RESOURCES/SUBSCRIPTIONS/RESOURCEGROUPS/WRITE"
| project TimeGenerated, OperationNameValue, ActivityStatusValue, ActivitySubstatusValue, ResourceGroup, Caller, CallerIpAddress, CategoryValue
| sort by TimeGenerated desc
```

The query returned the expected event with a successful status and created substatus.

The validation confirmed:

- the Log Analytics workspace was created successfully
- subscription Activity Logs were exported through diagnostic settings
- Activity Log categories were sent to Log Analytics
- a real management-plane event was generated
- the `AzureActivity` table received the event
- KQL could be used to investigate administrative activity
- useful audit fields such as caller, caller IP address, operation name, status, and resource group were available

## Real World Use Case

In a real organization, cloud security teams need visibility into administrative actions across Azure.

For example, if a resource group is deleted, a role assignment is created, a firewall setting is changed, or a policy assignment is modified, the organization needs a reliable way to investigate the event.

Centralizing Activity Logs in Log Analytics allows security teams to answer questions such as:

- who performed the action?
- when did it happen?
- from which IP address?
- what operation was performed?
- did the action succeed or fail?
- which resource or resource group was affected?

This lab demonstrates the foundation for that investigation workflow.

## Why This Matters in Practice

This lab reflects an important cloud security principle: logs must be centralized before they can support investigation and detection.

Activity Logs are useful in the Azure portal, but their value increases significantly when they are collected into Log Analytics. Once logs are centralized, they can be queried, retained, correlated, used in workbooks, connected to alerts, or later integrated with Microsoft Sentinel.

Without centralized logging, security teams may struggle to investigate incidents, prove audit evidence, or detect suspicious administrative behavior.

By configuring diagnostic settings and validating ingestion with KQL, this lab demonstrated a practical logging foundation for cloud security operations.
